    §2.3 Structural Models: What Is Connected to What?

    A structural model shows which parts of a system exist and how they relate to one another. We can ask, for example, which components depend on a service or where a document may be changed. To answer either question, we can set aside most of what happens inside the components.

    2.3.1 Entities, Relationships, and Graph Analysis

    Constructing a Structural Model

    Figure 2.3-1 shows the intended architecture of a web application with an API, a cache, and a database. Suppose we want to allow the cache to read from the database while requiring the web component to go through the API. How can we tell whether the architecture permits a bypass?

    Question. Can Web reach Database without passing through API? To answer, draw the four components and the dependencies between them. We can leave out the cache’s eviction policy and the database schema. Neither changes which components Web can reach in this model.

    Semantics. In Figure 2.3-1, each solid arrow denotes a permitted direct dependency between two components. A path is a sequence of components connected by those arrows. The crossed arrow marks a forbidden direct dependency and is excluded when tracing paths. Web therefore has an indirect route to Database through API and Cache.

    Analysis. Our architectural requirement is stronger than prohibiting a direct Web-to-Database dependency: every path from Web to Database must pass through API. Remove API and the arrows touching it from a copy of the graph. Start at Web and follow the remaining arrows. In this example Web has no outgoing arrow, so Database is unreachable. Now imagine adding a permitted dependency from Web to Cache. Removing API would leave the path Web → Cache → Database, showing exactly how the revised architecture would permit a bypass.

    Properties and Analyses

    Reachability asks whether a path connects one entity to another. Separation can require that no path connect two entities, or that they become disconnected when a designated boundary is removed. In Figure 2.3-1, Web is allowed to reach Database, but every route must pass through API. These properties help engineers identify who can reach a protected resource and whether a proposed architecture permits a bypass. Acyclicity requires a dependency graph to contain no directed cycles. In a finite, acyclic build graph, the tasks can be ordered so that every prerequisite finishes before its dependent begins. If two compilation tasks each require the other’s output, neither can go first. The dependencies must change before such an order is possible. Containment describes how entities are grouped, for example which modules belong to a service. Cardinality constrains how many relationships an entity may have, as when every service must have exactly one designated owner.

    The corresponding analyses are graph operations. Follow dependency arrows forward to establish reachability or backward to identify which components a change might affect. Remove a boundary node and search for a remaining path to test mandatory traversal. A cycle check determines whether a prerequisite order exists, and counting the ownership links of each service identifies any with missing or multiple owners. Each analysis depends on the meaning of the relationships: the dependency graph in Figure 2.3-1 can answer the bypass question, but checking ownership requires ownership links.

    The general procedure is to identify the entities and relationships relevant to a question, define what those relationships mean, and analyze the resulting graph. The same approach applies to a system’s environment, where we might trace communication pathways or dependencies between organizations, and to its internal structure. DocAble uses two such models of the same software: one to locate architectural boundaries and one to trace dependencies between computations.

    2.3.2 DocAble: Architecture and Computation Dependencies

    DocAble is a service that repairs accessibility problems in documents, such as missing alternative text, unmarked table headers, or incorrect reading order. The same operation may need a different implementation for a Word document and a PDF. Its structural models let engineers separate two questions: where format-specific changes belong, and how the repair computations depend on one another.

    Where may a document change?

    DocAble supports several document formats through libraries powerful enough to alter their underlying structures. Its architecture separates ordinary remediation logic from format-specific mutation through structured-document models. The Office formats use three models over a shared OpenXML foundation; PDF uses a separate model. The boundary is enforced differently across these implementations, but the architectural intent is common: document changes should pass through sanctioned mutation interfaces rather than arbitrary calls into format libraries.

    Document-mutation model · Structural

    • Engineering question — Where is document mutation supposed to occur?
    • Model — a layered structural relation: remediation logic operates through a structured-document model, with a separate implementation for each format: DOCX, PPTX, XLSX, and PDF.
    • Property — the intended architecture places format-specific mutation behind one sanctioned seam; ordinary remediation logic is not intended to bypass it.
    • Quality attribute — architectural integrity and modifiability.

    The necessary model is small. Figure 2.3-2 draws it: remediation logic operates through a structured-document model, which has a separate implementation for each format—DOCX, PPTX, XLSX, PDF, and others. It says nothing about queues, retries, deployment, user sessions, or the mechanics of individual repairs. Those facts are real but irrelevant to the question; the reduction preserves only the architectural boundary that matters.

    The principal property is the mandatory-traversal constraint introduced in Figure 2.3-1: every ordinary route to format-specific mutation must cross a sanctioned seam. In a sufficiently detailed dependency graph, we could remove that seam and ask whether remediation logic can still reach a raw mutation facility. Any remaining path would identify a bypass. DocAble instead uses format-specific static restrictions and runtime write-authority checks to protect these boundaries. Chapter 3 examines those controls.

    A structural model can become stale as the implementation changes. The code moves and the drawing does not, so the boundary it shows quietly stops matching the system. That gap between a model and the system it describes is model drift. Later sections make the correspondence explicit by deriving, generating, or tracing between model and implementation.

    What computations depend on one another?

    The document-mutation model identifies where changes belong. A second structural question concerns how remediation computations depend on one another. If we change one computation, which others might be affected? DocAble runs documents through registered remediation passes that detect conditions, produce information for later passes, decide whether work should proceed, or modify document state. A registered computation is a named remediation pass that DocAble knows how to invoke, such as a pass that classifies document content or repairs alternative text. The registry identifies the pass and records selected properties of its role in the pipeline. The graph represents the pass as a node, leaving its internal statements, library calls, and loops out of the graph.

    A repair pass may edit a document directly or produce a typed patch: a structured description of a proposed change, such as assigning alternative text to a figure. A separate component, the applier, interprets the patch and performs the change. The boundary where proposed changes become document mutations is the apply seam.

    Remediation-computation model · Structural

    • Engineering question — What computations make up remediation, and how does information move among them?
    • Model — a static directed graph whose nodes are registered computations and whose typed edges represent declared composition among them.
    • Property — Declared data and control dependencies are distinguishable and consistent with pipeline ordering. Each computation declares its mutation behavior: read-only, direct editing, typed patch production, or a combination of patch production and direct editing. Patch producers also identify where their patches are applied.
    • Quality attribute — analyzability, modifiability, and architectural integrity.

    DocAble's remediation-computation model distinguishes two relationships between registered computations. A data-flow edge means one computation produces information another consumes in producing its result. A control edge means one computation produces information another consults only to decide whether it should run. Figure 2.3-3 gives an example of each kind of typed composition: the classifier determines which repair passes run, while the repair passes produce patches that the patch applier consumes. The first relationship governs execution and the second carries data. Recording the edge type preserves that distinction. These distinctions make impact questions straightforward to investigate: the document-signals classifier has fifteen immediate control-gate dependents whose execution decisions may change with its output, while the intra-page vision-fusion pass has two immediate data-flow consumers. An engineer or agent can inspect these edges directly or traverse them to investigate indirect dependencies. Neither requires a dedicated analysis subsystem.

    The first model preserves one architectural relation. The second preserves a family of typed compositional relations over the same system.

    The model also declares each computation's mutation behavior. Some computations only inspect the document, some produce typed patches, some produce patches for part of their work and edit directly for the rest, and most edit document state directly. Patch producers also declare the seam through which their patches are applied. These attributes let an engineer ask which computations can modify a document directly and which produce patches for an applier. They describe the intended behavior of each computation; separate checks establish how closely the implementation follows those declarations.

    The computation model describes the declared computations and dependencies. Per-job invocations and retries belong to execution records. Other views can nevertheless attach observations to its stable computation identities. DocAble joins staged-run telemetry to those identities, so measured latency and cost can be queried alongside the structural model without turning the structural graph into an execution log. The per-session mutation record remains separate: it records what happened to one artifact, not the execution history of the computation graph.

    The same identities can support additional engineering views without enlarging the structural schema each time. Separate providers can record complexity, bounded execution, latency, test coverage, or checker trust against the same computation identity. Declared properties state engineering intent. Measured properties report observations and may have incomplete coverage. An unmeasured latency is therefore unknown, not zero. Joining these views lets engineers ask questions about combinations of properties while keeping each representation focused on its own question.

    The two structural models answer different questions about the same software. To investigate a possible bypass of the document abstraction, examine the architectural boundary and the paths that could circumvent it. To investigate a change to a remediation pass, follow its declared data and control dependencies and inspect its mutation behavior. Neither analysis requires a complete model of DocAble.

    A structural model earns its detail by the question it helps answer. Architectural paths, data dependencies, and control dependencies preserve different facts even when each is drawn with boxes and arrows. The next section adds time: what states a thing occupies, and what sequences of changes the model admits.
