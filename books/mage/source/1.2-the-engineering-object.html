    Chapter 1 — The New Engineering Problem  ::  §1.2

    §1.2 The Engineering Object

    1.2.1 Consequential Choices and Degrees of Freedom

    Delegating implementation is useful only if we can avoid doing much of the implementation work ourselves. Imagine asking an agent to build a feature. The first attempt fails, so we specify the data structures. The next attempt performs poorly, so we prescribe the indexes and queries. Then come the transaction boundaries, the function signatures, and eventually the variable names. Should we just write the code ourselves? How much direction, and of what kind, does an agent need to produce an acceptable result? We want to specify the decisions that matter without having to make all the decisions that implementation requires.

    When implementation is delegated, engineers must decide which choices to make and which to leave open. A function could be implemented in ten lines or ten thousand. A service could be built as a monolith or decomposed into microservices. Different algorithms, data structures, and architectures might all satisfy the same requirements. Some choices are better than others, but engineers need not make every choice in advance. They can specify the properties that matter and leave other decisions to the intelligence performing the work. Which choices can safely remain open is itself an engineering decision.

    Commodity intelligence can also change why an engineering choice matters. Consider the choice of a programming language. A human team might favor Java because its developers know it well. If agents can implement competently in several languages, that consideration weakens, while the ability to review their output may become more important. Meanwhile, a safety requirement may favor a language that provides a needed property, such as automatic garbage collection to reduce memory leaks caused by missing deallocation. A deployment target may also require a particular toolchain. These latter considerations persist regardless of who writes the code. The relevant question is what made the choice matter, and how those reasons change when agents perform the implementation.

    The same distinction applies at larger scales. Suppose a service needs persistent storage. If either a relational or nonrelational database can satisfy every property that matters, choosing between them may simply be a degree of freedom left to implementation. But if the system requires transactions across related records, a particular consistency model, or another property that distinguishes the alternatives, the choice becomes consequential. MAGE does not supply the database theory needed to make that judgment. It asks that the consequential property be represented—and, where necessary, enforced—rather than relying on each implementing agent to rediscover why the choice mattered.

    Notice the distinction between unmodeled and free. A choice is unmodeled when the engineering representations do not state it; it is free only when engineers permit the alternatives. Suppose the model says nothing about which database to use. If either database really can satisfy every consequential property, the omission represents a genuine degree of freedom. But if one alternative would violate a security, consistency, or performance obligation, the choice was never free. The engineering model simply failed to make the relevant obligation explicit.

    1.2.2 Engineering the Environment

    Engineers can externalize those decisions by shaping the environment in which agents work. As with printers, making productive machinery useful requires developing forms and ways of working around it. An engineering environment includes the representations, tools, processes, permissions, evidence, and mechanisms surrounding the agents’ work. In MAGE, a Governed Engineering Environment (GEE) deliberately carries engineering decisions forward by making consequential knowledge available, enforcing selected obligations, and preserving evidence needed for engineering control. Figure 1.2-1 shows how engineering leverage shifts from implementation toward this environment.

    Such an environment serves two different purposes: establishing consequential properties and reducing the cost of repeated engineering work. For assurance, models and checks can provide a manageable basis for evaluating a system even when an agent needs little help understanding its implementation. For efficiency, reusable representations can reduce the work agents spend recovering system knowledge. The two benefits may arise at different scales. Their value must justify the cost of building and maintaining the supporting structure.

    An engineering environment intended for agents need not mirror the one we have traditionally built for human developers. Agents can consume and maintain representations at scales that would be impractical for people. These representations also support analyses at a scale and level of detail previously impractical — and perhaps now necessary, given agents’ predilection for shortcuts. The design question is therefore two-sided: what existing engineering machinery should agents inherit, and what stronger machinery becomes practical because some of the workers are now machines?

    1.2.3 When Agents Produce the Wrong Result

    “’Tis a poor craftsman who blames his tools.” A 3D-printed bracket may fail because the printer lacks the required accuracy, but also because its design or fabrication instructions were unsuitable. Software agents blur this distinction because they can infer missing structure. A capable agent may produce an impressive result from a screenshot, prose request, or incomplete specification, filling in decisions that an engineer might otherwise have had to make explicit. That inferential capacity makes delegation useful, but it can also make omissions in the engineer’s work harder to notice. A completed artifact does not establish that the inferred choices satisfy the intended properties or reflect acceptable tradeoffs.

    When an agent produces the wrong result, start with what the engineer controlled: the instructions, representations, task boundaries, available tools, and required evidence. Were important properties missing? Did an instruction leave a decision open that should have been settled? Could the checks detect the error? Sometimes the foundation model simply lacks the necessary capability. Failed output alone does not establish that diagnosis.

    Abundant implementation raises the stakes. Capable agents can execute a bad direction with extraordinary speed. Velocity amplifies sound engineering and bad engineering alike.** My field notes on this point were less measured: “Claude is the fastest road to hell.”
