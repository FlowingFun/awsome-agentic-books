    Chapter 2 — Modeling  ::  §2.1

    §2.1 From Context to Engineering Models

    Context engineering can involve a modest form of modeling: selecting and organizing information that an agent needs to perform its work. The knowledge of a particular system might be distributed across source code, configuration, documentation, registries, version history, and the people who maintain it. An agent can reconstruct relevant knowledge from those sources, but doing so takes work, and another agent may need to repeat that work on a related task. Project instructions and agent skills can preserve selected knowledge across tasks. Some of these artifacts also represent engineering decisions, even when their meaning remains informal.

    AGENT HARNESS

    Inset — Skills and Project Instructions Can Be Engineering Models

    Project instructions record repository-specific conventions, architectural decisions, and obligations that should persist across tasks. Agent skills package procedures and resources for recurring work. Both preserve knowledge, but not everything they preserve constitutes an engineering model. Consider a project instruction such as “all database access must go through the service layer.” It expresses an architectural constraint, albeit imprecisely: the permitted dependencies remain open to interpretation, and violations cannot necessarily be detected mechanically. Now consider a skill specifying how an agent should commit changes and publish them to a remote repository. Its sequence of steps, preconditions, and failure-handling rules may encode a behavioral model of the publishing process, even if expressed entirely in natural language. In both cases, the representation preserves engineering decisions across tasks, but its informal semantics limit the precision with which those decisions can be analyzed or enforced.

    The form of the context matters as well as its availability. Natural language is inexpensive to write, expressive, and sufficient for many engineering questions. But when we rely on prose, two things must go right. The engineer must state the relevant distinctions clearly, and each later reader, human or agent, must interpret them correctly. Constructing an engineering model calls for deliberate choices about what to represent. The engineer must decide which entities, relationships, properties, or obligations a question depends on. Choosing the permitted values of a field, for example, can expose a case for which nobody has decided what the system should do. Recording the distinction explicitly gives later readers something to inspect and gives the engineer a decision to make.

    Engineers have long relied on models, even when those models were only partly explicit. Requirements, specifications, interface contracts, schemas, state machines, and architectural descriptions connect engineering questions to implementation decisions 12.1. Axel van Lamsweerde, Requirements Engineering: From System Goals to UML Models to Software Specifications (Wiley, 2009).2. ISO/IEC/IEEE, ISO/IEC/IEEE 42010:2022, Software, Systems and Enterprise — Architecture Description (International Organization for Standardization, 2022). A little whiteboarding followed by implementation can be economical when the same programmers do both and carry the remaining design knowledge in their heads. Agents working independently cannot reliably inherit those unrecorded decisions across tasks. Externalizing them gives agents a common representation to consult, while their ability to help construct, maintain, and query models changes the cost of keeping that knowledge available. The engineer must still decide which aspect of the system to represent and which distinctions the representation needs to preserve.

    2.1.1 Attributes of an Engineering Model

    Engineering models can describe a system, its environment, or the relationship between them. Before implementation begins, an engineer may model the workload a service will encounter and specify how quickly it must respond under that load. A threat model might identify the records the service must protect, the capabilities assumed of an adversary, and the trust boundaries separating components. Models can also describe internal organization and operation: an architectural model may specify permitted communication between services, while a worker-pool model may represent queues, worker assignments, and job lifecycles. The engineering question determines which relationships matter.

    Models can only be understood in context. Two important aspects of that context are scope and assumptions. Scope identifies what part of the system or its behavior the model represents; assumptions state conditions taken to hold when reasoning with it. For example, a worker-pool model might cover how jobs enter a queue, are assigned to workers, and complete, while omitting the work performed inside each job. An analysis of whether the queue will grow may assume a particular arrival pattern and distribution of service times. A conclusion derived under evenly spaced arrivals need not hold when requests arrive in bursts, even if the daily totals agree. Stating the scope and assumptions makes clear what the model can establish and where further evidence is needed.

    A further decision concerns the model’s authority. A descriptive model records what exists or has been observed; an authoritative model states properties that the system is required to preserve. An observed dependency graph records connections found in the implementation, while an authoritative architecture can use the same notation to declare which connections are permitted. The distinction matters when an agent proposes a change. The worker pool’s eight-worker limit might be a resource requirement or merely today’s tuning choice. The number in the code cannot establish its status. A descriptive model can record the current setting, while an authoritative model tells the agent which limit it must preserve.

    2.1.2 Purposeful Reduction and Engineering Freedom

    A model is a purposeful reduction of a system. It preserves the information needed to answer an engineering question and suppresses details that question does not require. A property that would require tracing thousands of implementation details may become a relation over a small graph, a transition over a finite set of states, or a bound over a measured quantity. The form of a representation affects which inferences a reasoner can readily draw from it 3.3. Randall Davis et al., “What Is a Knowledge Representation?” AI Magazine 14, no. 1 (1993): 17–33, https://doi.org/10.1609/aimag.v14i1.1029.

    Choosing the Level of Detail

    Choosing a model also means choosing its granularity. Engineers examining service boundaries may need only services and their dependencies. A maintainer changing one interface may instead need the classes or functions that use it. Engineers can maintain both views, choosing the level of detail that the question and the people or agents asking it require.

    A model can retain too much or omit too much. Suppose an architectural model represents a web application and its database but omits the service layer between them. The omission conceals a consequential boundary: the model cannot distinguish permitted database access from a direct call that violates the intended architecture. At the other extreme, a model intended to show service boundaries might include every class, method, and internal dependency. That excessive detail hampers analysis and complicates comprehension. The appropriate level of detail depends on the engineering question.

    Obligations and Degrees of Freedom

    A model is not the system it represents. An engineering model can specify what a system must accomplish without prescribing every detail of its implementation. Engineering obligations constrain the set of acceptable implementations. A tolerance specifies variation in a resulting property that the engineer will accept. A degree of freedom is a choice the implementer can make while satisfying those obligations. For example, a service may have to respond within 200 milliseconds. That timing tolerance constrains the result, but does not prescribe the algorithm, data structures, or internal organization used to achieve it. Those implementation choices remain open insofar as they satisfy the timing requirement and the system’s other obligations.

    Suppose a list of up to 1,000 names must be returned in alphabetical order within 200 milliseconds. Figure 2.1-1 represents the possible implementations and the two obligations they must satisfy. Only implementations within the overlap satisfy both obligations. The 200-millisecond tolerance bounds response time; the choice among sorting algorithms that meet both requirements is a degree of freedom.

    How much should you leave open? Recall from Chapter 1 that agents can investigate alternatives and perform substantial work much faster than a human engineer. Sometimes the right engineering decision is not yet known. Rather than settle it prematurely, you can delegate the work needed to find out. An agent might measure a workload, construct a performance model, or benchmark candidate sorting algorithms on representative inputs. The resulting evidence can inform a decision by the engineer or the agent. Prescribing an algorithm before that evidence is available substitutes a guess for an informed choice. Ultimately, the engineer still determines which results are acceptable and which obligations the chosen implementation must satisfy.

    Scaffolding the Implementer

    An engineering model may establish the obligations without providing enough guidance for a particular implementer to satisfy them. A less capable agent, much like a junior engineer, may need examples, a decomposition, or intermediate constraints to interpret the model and realize an acceptable implementation. This additional guidance is scaffolding: it helps the implementer satisfy the obligation without changing the obligation itself.

    Figure 2.1-2 distinguishes the engineering obligation from the scaffolding a particular agent requires. An agent capable of designing a suitable benchmark may need only the workload and timing requirement. Another may need an example showing how to exercise the full range of list sizes. Such examples should guide implementation without becoming permanent restrictions. If a particular algorithm must be preserved, the engineer must state that requirement; otherwise, an agent may mistake an incidental implementation choice for an essential one.

    As you model a system, you may make the unpleasant discovery that you are not perfect. A choice omitted from a model is not necessarily a genuine degree of freedom. If an implementation would cause you to say, “NOT THAT!”, you have discovered a consequential boundary that the model left implicit. Uncertainty is different again. A degree of freedom permits a choice among alternatives known to be acceptable; an unresolved question means we do not yet know which alternatives are acceptable. We can record what is known, investigate the uncertain cases, and revise the model when new evidence reveals a distinction we had not thought to specify.

    A useful model must therefore be judged both by what it preserves and by what it leaves open. To test adequacy, start with the question and ask whether the model distinguishes cases that require different answers. To test parsimony, start with the model and ask whether any distinction could be removed without impairing that purpose. Both judgments may change as engineers learn more about the system. The work a model saves must justify the effort of constructing and maintaining it.

    2.1.3 Models Are Not a Silver Bullet

    Modeling is not a silver bullet, to borrow Brooks’s phrase 9.9. Frederick P. Brooks, “No Silver Bullet: Essence and Accidents of Software Engineering,” Computer 20, no. 4 (1987): 10–19. Agents and humans can misinterpret natural-language instructions, but they can also misunderstand or misuse engineering models. An agent may reuse a model outside its intended scope or mistake an observed implementation choice for an authoritative requirement. The model itself may omit a consequential distinction or encode an incorrect assumption. Greater structure and semantic precision can make some errors easier to detect, but they cannot establish that the representation captures what the system ought to do. A model can be internally consistent and support a correct analysis while still giving the wrong answer to the engineering question.

    The purpose of modeling is to reduce these risks, not to eliminate engineering judgment. Engineers must decide which distinctions deserve representation, which assumptions remain valid, and which implementation choices can safely remain open. Agents can help construct and analyze models, but neither their apparent confidence nor the precision of the representation establishes that the underlying requirements are correct. Understanding those requirements still depends on the system’s purpose, its operating environment, and feedback from the people who use it. A model earns its place by the question it settles, not by how much of the system it represents. The next section examines how engineers construct, revise, and use models to answer those questions.
