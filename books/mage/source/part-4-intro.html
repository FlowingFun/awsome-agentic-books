    Chapter 4

    MAGE in Motion: Engineering Through Models

    Chapters 2 and 3 separated Modeling from Alignment so that each principle could be examined clearly. This chapter brings them together around a practical question: how should we put models to work as a system evolves? Analysis can suggest a different design; a prototype can reveal that the current model omits a consequential interaction. Engineers must decide which properties to protect while exploring a change, how to evaluate the result, and what to retain for later work.

    Key Ideas

    Model → Realize → Evaluate.

    Make consequential knowledge and intent explicit. Build or modify the system, potentially through agents. Evaluate the result against the relevant obligations, returning to the models or realization as the evidence requires. Alignment operates throughout, establishing or preserving correspondence as the system changes. Governance conversion makes consequential lessons durable in the structure that later work inherits.

    You can enter this cycle at any point. Recall Figure 2.2-1 in Chapter 2: engineering may begin with requirements, an existing system, an observed failure, or exploratory agent implementation.

    §4.1 explains how engineers introduce models incrementally and protect established properties while exploring change. §4.2 follows that process through DocAble’s memory and execution problems; §4.3 shows how to recover useful models from an existing system. §4.4 turns to equipping, evaluating, operating, and maintaining the environment that later work inherits.

    Inset — Spec-driven development and engineering through models

    Spec-driven development (SDD) provides workflows for organizing implementation and evaluation around specifications. These workflows can support MAGE, but do not replace its broader concern with modeling consequential properties and enforcing selected engineering obligations as a system evolves.

    In SDD, explicit specifications guide agentic implementation and evaluation. The tools organize that work in different ways 1.1. Shyam Agarwal et al., Spec-Driven Development as Prescribed and as Practiced, 2026, https://doi.org/10.48550/arXiv.2608.25202. GitHub’s Spec Kit argues for specifications as primary artifacts from which code is derived 2.2. GitHub, “Specification-Driven Development (SDD),” accessed November 6, 2026, https://github.com/github/spec-kit/blob/main/spec-driven.md. OpenSpec preserves capability specifications while recording proposed and completed changes; Conductor combines shared project context with specifications and plans for individual changes 34.3. Fission AI, “OpenSpec: Concepts,” accessed November 6, 2026, https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md.4. Keith Ballinger et al., “Conductor: Introducing context-driven development for Gemini CLI,” Google Developers Blog, December 17, 2025, https://developers.googleblog.com/conductor-introducing-context-driven-development-for-gemini-cli/. Specifications can evolve as implementation and operating experience expose missing requirements.

    Test-driven development (TDD) offers a useful analogy: its test → implement → refactor cycle organizes programming, while the team still has to decide how to evaluate interactions and the assembled system 5.5. Martin Fowler, “Test Driven Development,” December 11, 2023, https://martinfowler.com/bliki/TestDrivenDevelopment.html. TDD can also be understood as a form of specification-first development: tests express selected requirements as executable checks of a component’s observable behavior before its implementation is written. The implementation remains free to change as long as it satisfies those checks. The specification is necessarily partial, since tests exercise only selected inputs and properties, but the underlying move is familiar: establish what must hold, then evaluate the implementation against it. An SDD workflow similarly contributes to engineering a system without settling every question about its representations, obligations, and evidence.

    MAGE examines how cheaper model construction, analysis, and maintenance change which engineering work is worth doing. As a system grows, separately specified changes can interact through shared resources and dependencies. In DocAble, for example, increasing concurrency could improve throughput while also increasing peak memory. Concurrency models used the memory model to choose how much work could run at once, and guards refused work whose estimated memory exceeded its budget. Later measurements corrected assumptions in the model. §4.2 follows this example from the memory failure that made the model necessary.
