    §2.6 System Knowledge: Connecting the Models

    Different questions require different views of the same system. Following Fairbanks, we understand software architecture as the structures needed to reason about a system, including the software elements, the relations among them, and properties of both 1.1. George Fairbanks, Just Enough Software Architecture: A Risk-Driven Approach (Marshall & Brainerd, 2010). A component view exposes decomposition, a behavioral view shows legal transitions, a deployment view records allocation, and a quantitative view can supply a resource bound. An architectural decision can draw on several of these views. To decide whether two workers can share a host within its memory budget, for example, an engineer needs to know which workers may run together, how much memory each needs, and how much the host provides.

    The views need to agree on the identities and relationships that their questions cross. A deployment record and a memory budget can each serve its own purpose if the engineer can identify the workers and host in both. MBSE methods likewise connect requirements, design models, analyses, and verification results so that engineers can follow a decision across representations 22. Jeff A. Estefan, Survey of Model-Based Systems Engineering (MBSE) Methodologies, INCOSE-TD-2007-003-02 (International Council on Systems Engineering (INCOSE), 2008). 3.3. Azad M. Madni and Michael Sievers, “Model-Based Systems Engineering: Motivation, Current Status, and Research Opportunities,” Systems Engineering 21, no. 3 (2018): 172–90, https://doi.org/10.1002/sys.21438. When these views are cheap to derive, maintain, and query, more of that knowledge can remain explicit between tasks.

    2.6.1 Connecting Models to Answer Engineering Questions

    Models can be connected across different concerns or across levels of abstraction. A service catalog, deployment model, and measurement record provide different views of the same service; joining them connects information that no individual view contains. A service-level architecture and a module-level dependency graph instead describe related structure at different levels of detail. The latter introduces classes, interfaces, and dependencies omitted from the former, but must preserve any architectural boundaries established by the higher-level model.

    The relationship between abstraction levels recalls the classical technique of stepwise refinement 44. Niklaus Wirth, “Program Development by Stepwise Refinement,” Communications of the ACM 14, no. 4 (1971): 221–27, https://doi.org/10.1145/362575.362577.: progressively transforming an abstract description into a more detailed realization while preserving its required properties. In agentic engineering, an agent can perform much of this refinement, choosing algorithms, data structures, and internal organization within the freedom left by the higher-level model. The engineer remains responsible for deciding which properties must survive that translation. Explicit relationships between abstraction levels make those obligations available for analysis and checking rather than relying on the agent to infer them correctly.

    A shared service identifier can connect a catalog entry to a deployment and its measurements without requiring those records to share a file format.

    Suppose an agent is investigating a slow report service. The service catalog identifies its owner, the deployment model records its resource allocation, and a measurement record supplies recent response times. Shared service identities let the agent connect these representations and obtain the relevant facts without reconstructing their relationships from source code or directory names.

    The deployment model describes where the service runs and what resources it has been assigned; an execution history records what happened during particular requests. Joining measurements from that history to the service identity can reveal a performance problem without turning the deployment model into a log. Why not combine all these representations into one comprehensive description? Taken to its extreme, that description would read like the implementation itself, with all the detail that modeling was intended to suppress. Separate models preserve the distinctions needed for different questions; their connections let engineers reason across those distinctions without carrying every detail into every analysis.

    Some answers require a join. Suppose the policy allows a report service to invoke a renderer. The policy names the two services, while the deployment model records the runtime identity under which the report service runs. Joining the permitted call to that identity determines which principal needs permission to invoke the renderer. Neither model contains that complete answer by itself: the policy does not name the environment's principal, and the deployment record does not decide which calls should be permitted.

    A model can also connect an obligation to its evidence. A latency requirement might identify the workload and response-time bound, while a test catalog identifies the measurement that evaluates them. Linking the requirement to that test makes a missing measurement visible. SysML represents this relationship through verification cases that identify the subject and the requirements to be evaluated 5.5. Object Management Group, OMG Systems Modeling Language (SysML), Version 2.0, OMG Document formal/26-03-02 (Object Management Group, 2026), https://www.omg.org/spec/SysML/2.0. Whether the test supplies adequate evidence, and whether its result should block release, remain further engineering decisions.

    A join only works if it preserves the distinctions the decision needs. A record may use the correct user identifier and still reduce an unlimited entitlement to a finite-credit balance. Shared identity makes the connection explicit; it does not guarantee that the information passed across it is adequate.

    An engineer or agent can therefore enter through the object named by a task and follow the relations its question requires: from service to owner, from service to deployment, from deployment to measurement. A query interface makes these connections traversable. The agent needs the connected slice that answers the question, rather than every model in the project.

    2.6.2 Maintaining Correspondence

    Prefer shared identity and derivation over independently maintained copies of the same fact. A deployment record can refer to the service catalog's identifier rather than copying the service's description and owner. A report can join the two records when it needs their combined information. Where a second representation must contain a copy, make its source and correspondence check explicit. Otherwise every copy becomes another fact engineers must remember to update.

    Models and implementations can fall out of correspondence as a system changes. Maintaining their relationships requires deciding which representation is authoritative for each property and how correspondence with other representations should be established and checked. Figure 2.6-1 distinguishes three arrangements:

    • Derive from implementation. A dependency graph extracted from call sites describes the connections found in the code. A drift check can repeat the extraction and compare the result with a maintained view. Agreement covers the relationships the extraction observes.
    • Generate from models. An authoritative schema can generate the types used by interface clients. A freshness check compares the checked-in types with the current generator output. The schema determines those types while leaving the client’s algorithms open.
    • Trace and check correspondence. A behavioral model might specify permitted transitions while leaving their implementation to an agent. Traceability links each modeled transition to the functions that implement it. A check can establish that a referenced function still exists; whether it implements the transition correctly requires further evidence.

    An authoritative model can also be interpreted directly during execution. Consider the build with two independent compilations and one link task. The runner reads the declared dependencies to start each compilation when it is ready and to delay linking until both object files exist. Nothing has to generate a schedule in advance. An engineer can query those same dependencies to find which task a changed object file could affect.

    The third arrangement is particularly useful when agents implement systems whose models specify only selected properties. The models preserve engineering decisions while leaving other implementation choices open. The three arrangements can coexist within one system, and their coverage can change as engineers learn which properties need explicit representation. These correspondence patterns apply between models at different abstraction levels as well as between models and implementation; a refinement relationship identifies which higher-level properties a more detailed representation must preserve.

    2.6.3 DocAble: Connecting Engineering Models

    DocAble improves document accessibility through passes that analyze or change a document. Workers and services execute those passes, and the product retains evidence about the resulting artifact. Its modeling problem therefore crosses several views: the intended computation, the execution arrangement, and what one run actually changed. The worked question is how those views can share facts without becoming independent accounts that drift apart.

    DocAble uses different representations for different engineering questions. Roughly 130 structured model records and several data dialects describe components, deployment, data flow, behavior, and governance. Shared identities let an engineer move among these records as a question requires. Figure 2.6-2 follows the slow service from its registry entry to its deployment and then to performance measurements.

    The models are represented as data rather than importing the implementation they describe. Keeping the representations separate lets engineers check their correspondence. Where a model is intended to provide independent evidence about an artifact, the model must remain distinguishable from that artifact. Chapter 5 shows how these models are maintained and used in the governed engineering environment.

    One Dependency for Execution and Analysis

    Suppose we change a remediation pass. Which later computations depend on its output, and will they still execute in the required order? In [ref:chapter:2.3-structural], we introduced DocAble's remediation-computation graph for investigating dependencies. Connecting those dependencies to the execution declarations lets us examine their scheduling consequences without reconstructing the pipeline from code. For a DOCX job with table-header repair enabled, one pass marks table headers and another checks the table's structure. The registry declares that the repair pass writes table-header information and that the structure check reads it.

    Matching that write to that read gives a dependency: repair must precede the check. The scheduler uses the dependency to order the work, so the check examines the table after the header pass has run.

    The Office registry also emits its resource dependencies for a separate Python graph view. The edge from table-header repair to the structure check therefore comes from the same read/write metadata used by scheduling. An engineer can inspect which computations depend on table-header information, or join their identities to measurements, without executing the remediation pipeline. The Python graph provides the analytical view; the execution machinery does not schedule from it.

    PDF uses a different connection. Its analytical edges are projected from parallel typed declarations of what each pass produces and consumes, including information consulted only to decide whether a pass runs. Blocking checks hold those declared relationships in correspondence with the executable pipeline.

    The Office example makes the same dependency available for execution and analysis; it does not derive a new relationship by joining independent models. The execution machinery uses the declared relationships to schedule work; the analytical view exposes the structure needed for queries and checks. The important question is which representation owns each fact and how each consumer remains connected to that source. Where separate declarations are necessary, as in the PDF view, checked correspondence carries that connection.

    What One Document Run Changed

    A static computation graph does not record the mutations performed during a particular run. DocAble records consequential document changes as typed operations: each operation names its target, the mutation made, the responsible remediation pass, and the retained evidence. That history supports audit, debugging, and a changelog. Recording only “document modified” would lose the very distinctions those uses need.

    During a PDF remediation session, typed edit values form a per-session log. A replay engine can apply the same sequence deterministically. This record preserves the mutations while omitting the reasoning, analyses, control decisions, and retries that produced them. The computation graph asks what may compose; the edit record asks what happened to this artifact. Figure 2.6-3 contrasts these two reductions.

    DocAble’s PDF changeset interface also represents edits before they happen. A changeset is an ordered collection of typed operations, each naming a target and a supported mutation, such as assigning alternative text or changing a structural tag. The proposing computation does not manipulate PDF objects directly. An applier resolves the targets against the current document and returns a result for each operation. The proposal expresses intended mutations; the results and attribution record show what was actually applied.

    A specialized remediation pass, a general-purpose agent, or a human editor can propose operations using the same vocabulary. The interface preserves the information needed to apply and inspect the change while leaving its producer’s reasoning unspecified. Chapter 3 examines the constraints on applying such proposals; Chapter 5 returns to the reasoning strategies that can produce them.

    DocAble joins staged-run latency and cost to stable computation identities, so measurements can be queried alongside the static graph. The per-session edit log remains a separate provenance record; it is not a per-run execution graph over computation nodes. Recording attribution is also distinct from ensuring that every mutation records it. A structural check requires typed mutation operations to emit attribution, but it cannot establish that the semantic explanation inside the record is correct.

    Joining a Call to Its Deployment Permission

    A permitted interservice call requires several models to agree. A typed edge records that one service may call another. Deployment configuration identifies the environment variable carrying the callee's URL. The caller's runtime identity determines which invocation grant the cloud's access-control configuration must contain. Joining the edge to these records determines both how to reach the callee and who is permitted to invoke it; a further comparison checks agreement with the service catalog's documented topology. Twenty-eight modeled call edges produce ten distinct invocation grants once shared runtime identities are accounted for. No single source artifact contains that deployment plan.

    DocAble introduced the join after service URLs were wired correctly but the matching invocation grant was absent, taking staging down with authorization errors. The repair made URL wiring and authorization two consequences of the same modeled edge, so a later change could derive them together rather than requiring another bespoke grant.

    Connections can create information that no individual model contains. The call model does not contain the environment-specific runtime identity; the deployment environment does not independently state the intended call topology. Joining them determines the permission that should exist.

    Each connection has a specific purpose. Resource declarations supply a dependency, computation identities connect measured cost to a pass, an edit record explains a document change, and a call joined to a deployment identity determines a permission. Keeping those relations explicit lets engineers inspect the connection that an analysis depends on, instead of treating membership in a model family as evidence that the models agree.
