    §3.3 Governance Mechanisms

    Return to the billing architecture: Reporting may obtain data through BillingAPI, but must not connect directly to BillingDB. Keeping that boundary lets the billing service control access to its data and change its schema without exposing it to every client. The architectural model states the permitted relationship. How can the engineered environment preserve it while agents change the reporting code?

    Governance mechanism. A repeatable structure in the engineered environment that constrains agentic work, produces evidence about it, or controls whether it may proceed.

    Table 3.3-1 distinguishes the three governance functions introduced in Figure 3.0-1 by the engineering questions they answer.

    Table 3.3-1. Three functions of engineering governance. Constraints restrict what can happen; sensors provide evidence about what has happened or is proposed; gates determine what may proceed. A single mechanism may perform several functions. This classification draws on established principles of protection and policy enforcement 123.1. Jerome H. Saltzer and Michael D. Schroeder, “The Protection of Information in Computer Systems,” Proceedings of the IEEE 63, no. 9 (1975): 1278–308.2. Raj Yavatkar et al., A Framework for Policy-based Admission Control, RFC no. 2753 (RFC Editor, 2000), https://doi.org/10.17487/RFC2753.3. OASIS, eXtensible Access Control Markup Language (XACML) Version 3.0 Plus Errata 01, OASIS Standard incorporating Approved Errata, ed. Erik Rissanen (OASIS, 2017), https://docs.oasis-open.org/xacml/3.0/errata01/os/xacml-3.0-core-spec-errata01-os-complete.html.

    ConstraintWhat can happen?Restricts available actions or states.
    SensorWhat evidence do we have?Produces evidence about artifacts, proposed actions, or executions.

    SOFTWARE ENGINEERING

    Inset — Familiar Engineering Machinery

    Constraints narrow what an implementation or actor can do. Type systems and module boundaries can exclude invalid expressions or hide operations from callers; database constraints and permissions can restrict stored states or resource access. Their assurance depends on the scope they actually enforce. A type-level restriction governs checked code, for example, while inputs from outside that code still need to be checked at the boundary.

    Sensors make evidence available for inspection, so their usefulness depends on observability. Logging and tracing expose execution behavior; parsers and static analyses can expose facts about artifacts, configurations, and dependency graphs. The evidence must preserve the distinctions needed by the check, whether it comes from a running system or a static artifact. Collecting it does not itself determine whether work may proceed.

    Gates evaluate conditions and enforce decisions at boundaries. A continuous integration (CI) job may report test results; a merge gate uses required results to admit or refuse a change. Deployment gates can require a successful security check, and runtime authorization gates can permit or refuse requests under an access policy. One tool can perform several functions by collecting evidence, evaluating it, and enforcing the resulting decision.

    Let's follow a proposed reporting change from implementation to merge. Figure 3.3-1 shows how module restrictions, test instrumentation, and a merge gate work together to preserve the billing boundary.

    3.3.1 Prevention and Observation

    A constraint can exclude some violations before they occur. Sensors provide evidence about behavior that remains possible, so the environment can check it before accepting the change.** For the role of constraints and feedback in systems-safety engineering, see Leveson 4.4. Nancy G. Leveson, Engineering a Safer World: Systems Thinking Applied to Safety (MIT Press, 2011).

    Why observe a behavior when we could prevent it? Because we may not yet know whether it should be forbidden. A constraint embodies a decision about which alternatives are unacceptable. If that decision is premature, the constraint can exclude useful implementations along with bad ones. Observation lets us gather evidence before deciding what to prohibit. Once an obligation is understood, however, relying on observation alone may leave a known failure free to recur. The engineering judgment is deciding which choices are settled and which still warrant investigation.

    An instruction to use the billing API can guide an agent, but it does not exclude a direct database connection. A constraint instead limits the actions or states available to the implementation.†† Types provide one familiar way to exclude invalid choices. Pierce describes type systems as syntactic methods for ruling out classes of erroneous behavior 5.5. Benjamin C. Pierce, Types and Programming Languages (MIT Press, 2002). A closed enum with variants such as IDLE, RUNNING, and DONE excludes undeclared state names in checked code; external input must be validated when converted to the type. It does not by itself forbid a transition from IDLE directly to DONE. That transition requires its own constraint. For the reporting change, a module boundary exposes the billing API client while keeping the database connector private. The language's visibility rules prevent checked reporting code from importing that connector. The agent remains free to assemble the report but cannot use the private connector. Generic networking remains a possible route around this restriction.

    Constraints can restrict an implementation after it is produced, or shape its construction so that selected violations cannot arise. Classical model-driven engineering offers a familiar example: a generator translates a model into code, configuration, or other artifacts. If an architectural model determines which services may communicate, generated interfaces or access-control rules can embody those relationships directly. For the properties preserved by the transformation, Alignment is achieved by construction rather than by checking an independently produced implementation afterward 678.6. Douglas C. Schmidt, “Model-Driven Engineering,” Computer 39, no. 2 (2006): 25–31, https://doi.org/10.1109/MC.2006.58.7. Shane Sendall and Wojtek Kozaczynski, “Model Transformation: The Heart and Soul of Model-Driven Software Development,” IEEE Software 20, no. 5 (2003): 42–45, https://doi.org/10.1109/MS.2003.1231150.8. Krzysztof Czarnecki and Simon Helsen, “Feature-Based Survey of Model Transformation Approaches,” IBM Systems Journal 45, no. 3 (2006): 621–45, https://doi.org/10.1147/sj.453.0621.

    A generator can produce selected parts of an implementation, leaving other decisions to agents. An agent can also customize or extend generated code, provided those changes preserve the obligations embodied in it. The model must express the intended obligation, the generator must preserve it, and subsequent changes must not bypass the generated structure.

    Agents can also help construct the checking and enforcement machinery. Once an invariant is explicit, an agent can help translate it into a lint rule, schema constraint, architectural test, or static analysis. Here the generated artifact checks or constrains another implementation. Bodden’s work on self-adaptive static analysis proposes automatic optimization of an analysis from an explicit representation of it 910.9. Eric Bodden, “Self-Adaptive Static Analysis,” Proceedings of the 40th International Conference on Software Engineering: New Ideas and Emerging Results (New York), ICSE-NIER ’18, 2018, 45–48, https://doi.org/10.1145/3183399.3183401.10. Eric Bodden, Self-Optimizing Static Program Analysis (SOSA), ERC Advanced Grant 2023 Research Proposal, Part B1 (Paderborn University, 2023), https://www.uni-paderborn.de/fileadmin-hni/sse/sosa/SOSA.pdf. The engineer remains responsible for the obligation and for validating what the resulting mechanism actually establishes.

    A sensor produces evidence about work or system behavior through mechanisms such as logging, instrumentation, and static analysis, and so depends on observability: the relevant state or behavior must be exposed in a form the environment can inspect. For the reporting change, instrumented tests record the caller, destination, and outcome of attempted connections. A test exercising a direct database path through generic networking can expose a violation that the module restriction did not exclude. Recording the connection does not prevent it; the evidence informs the acceptance decision. The record must distinguish an API call from a direct database connection. “Request succeeded” is insufficient: the evidence must preserve the distinctions needed to evaluate the architectural obligation.

    3.3.2 Gates: Evaluation and Enforcement

    A gate evaluates a condition and permits or refuses passage, drawing on evidence it checks directly or receives from another checker. The merge gate requires passing build checks and test interactions consistent with the architectural model. A direct database connection fails the interaction check even when the code passes the module restriction. A failed or missing required check blocks the merge. Passing establishes only that the candidate satisfied these admission conditions; the tests cover only the executions they exercised.

    These categories describe functions rather than execution stages. A source scanner can act as a sensor, runtime permissions as constraints, and one tool may combine observation, evaluation, and refusal. Together, the module restriction and instrumented tests provide defense in depth 1111. Ron Ross et al., Engineering Trustworthy Secure Systems, NIST Special Publication 800-160, Volume 1, Revision 1 (National Institute of Standards; Technology, 2022), https://doi.org/10.6028/NIST.SP.800-160v1r1.: a connection that evades the former may be detected by the latter and rejected at merge. The gate does not independently detect violations; it enforces the test verdict. Engineers must still consider which paths escape both protections.

    A human reviewer might recognize the forbidden connection and refuse the merge using tacit knowledge of the architecture. With agents making repeated changes, engineers can instead record the permitted interaction, collect evidence, and make acceptance depend on the check. The engineer still decides which obligations warrant enforcement.

    Evidence must also correspond to the candidate being accepted. A release check can regenerate it rather than trust the producing agent’s report or results from an earlier revision.‡‡ Repeating the check costs computation and time. Reusing or caching an earlier result can be sound when the system establishes that the relevant inputs have not changed. This makes acceptance independent of the agent’s account of its work.

    Constraining Document Changes

    DocAble’s PDF changeset interface provides an action boundary for document repair. A reasoning component may decide that an image needs alternative text without receiving unrestricted access to the PDF’s internal representation. It proposes a typed operation naming the target and intended change. The operation vocabulary constrains which mutations can be expressed through this interface; the applier determines whether a supported operation can proceed against the current document.

    The applier’s refusals make that boundary concrete. An operation that marks a structure as decorative must identify the source of the classification. The applier refuses it if the classification source is missing, or if the target is a heading, a formula, or content carrying authored alternative text. These are checks with enforced outcomes. Subsequent validation supplies evidence about selected properties of the resulting document, including content preservation and mechanically testable accessibility requirements. A well-formed proposal does not establish that its description is educationally appropriate, and successful application does not establish complete accessibility.

    The boundary also preserves freedom. A specialized pipeline and a general-purpose agent may use different methods to decide what to repair. Neither needs to reproduce the mechanics of applying a supported edit. Nor does either gain authority to bypass the restrictions imposed by the common interface. The architecture is therefore more than a convenient API: it separates the judgment that proposes a change from the mechanisms that determine which changes can be made and which results are acceptable.

    3.3.3 Tests and Models Work Together

    The reporting-service boundary concerns relationships among components. The job-lifecycle state machine supplies a constructive account of behavior: it specifies how a job’s state should change in response to events. That meaning can guide implementation and provide expected outcomes for tests. The testing task is to compare those expectations with what the implementation actually does.

    Consider a more demanding job protocol in which workers claim queued jobs under expiring leases. Worker A’s claim expires, worker B acquires a newer claim, and A then tries to release its old one. A regression test can reproduce that sequence against the implementation and assert that B remains the owner. It preserves a concrete failure scenario and makes a recurrence easier to diagnose. Such tests remain useful as the system acquires more explicit models 12.12. Titus Winters et al., Software Engineering at Google: Lessons Learned from Programming Over Time (O’Reilly Media, 2020).

    We can also state a property covering many such cases: a release carrying an old generation must not clear the current claim. Property-based testing supplies generated inputs to a check of that property, varying worker identities, claim generations, and relevant operations. The engineer must choose the property and ensure that the generator exercises the cases that matter, including stale releases. QuickCheck provides a framework for expressing and testing such executable properties 13.13. Koen Claessen and John Hughes, “QuickCheck: A Lightweight Tool for Random Testing of Haskell Programs,” Proceedings of the Fifth ACM SIGPLAN International Conference on Functional Programming (ICFP 2000) (New York, NY), 2000, 268–79.

    An explicit model adds a reusable account of the behavior those tests should expect. For this ownership question, the model might retain each job’s current owner, claim generation, and whether the claim has expired, together with the effects of claiming, reclaiming, and releasing. A model-based test can use that account to construct sequences of operations and compare the implementation’s responses with the permitted outcomes. The model can help choose what to exercise, provide the test oracle—the rule for evaluating the result—or do both. This does not require a second implementation of the database. It requires enough behavior to answer the ownership question 14.14. Mark Utting et al., “A Taxonomy of Model-Based Testing Approaches,” Software Testing, Verification and Reliability 22, no. 5 (2012): 297–312, https://doi.org/10.1002/stvr.456.

    A test driver can issue each operation to both the ownership model and the real lease implementation, then compare their ownership states. An attempted stale release must leave the current claim unchanged in both. The driver translates model operations into real calls and observes their results; the same model supplies expectations across many sequences. A sequential driver will not expose every race inside those calls: concurrent schedules and database atomicity need their own tests or analysis 15.15. Wolfgang Prenninger and Alexander Pretschner, “Abstractions for Model-Based Testing,” Electronic Notes in Theoretical Computer Science 116 (2005): 59–71, https://doi.org/10.1016/j.entcs.2004.02.086.

    Hypothesis’s stateful testing can generate sequences of actions and compare a real system with a simpler model, combining property-based and model-based testing. A useful failing sequence can then become a fixed regression test 16.16. Hypothesis contributors, “Stateful Tests,” Hypothesis, accessed November 5, 2026, https://hypothesis.readthedocs.io/en/latest/stateful.html.

    Model coverage, code coverage, and the properties checked answer different questions. Exercising every modeled transition may miss a problematic ordering; executing every relevant line may still leave ownership unasserted. Passing tests supports a claim only about the executions and properties checked 12.

    The extra model also has a cost. Engineers must validate its rules against the requirements, maintain the connection to the implementation, and revise it when the intended behavior changes. Copying implementation logic into the expected-result calculation can reproduce the same mistake on both sides. A separate model earns its keep when a simpler statement of the behavior makes tests easier to select, results easier to evaluate, or recurring obligations easier to maintain. For a small local rule, a direct assertion may already be sufficient.

    3.3.4 Model and Exercise Failure Responses

    Models can guide tests of failure handling as well as successful operation. Failure Mode and Effects Analysis (FMEA) provides an established approach: enumerate the ways a component or operation can fail, identify their causes and effects, and assess their consequences 17.17. International Electrotechnical Commission, IEC 60812:2018: Failure Modes and Effects Analysis (FMEA and FMECA), IEC 60812:2018 (International Electrotechnical Commission, 2018). DocAble’s failure models focus on services in its web layer. In this service-oriented architecture, we represent each relevant failure with an identity, its originating operation or dependency, the condition that produces it, and the response required of the receiving service. A timeout, an invalid response, and a rejected request may all interrupt work, but they need not call for the same response.

    DocAble uses the failure model to guide fault-injection tests. The tests inject modeled failures at dependency boundaries while exercising the real service implementation, then inspect the result returned to the caller and the response of downstream consumers. They also exercise healthy operation, so a test cannot pass merely because every request fails. Where a failure affects admission, the test checks whether the required consequence follows. Reproducing existing behavior does not establish that the behavior is acceptable.

    The model also supports failure provenance. When a failure occurs, DocAble can record where it originated, where it was observed, and how it propagated through subsequent operations. These records let engineers trace a failed request through the affected services rather than reconstructing its history from unrelated error messages. The model need not enumerate every possible fault; DocAble concentrates on failures affecting recovery, correctness, and the trustworthiness of evidence, extending the representation when new cases emerge.

    This approach exposed an incorrect interpretation of output from DocAble’s accessibility checker. If the underlying validation program timed out or failed to run, the checker could report an informational issue while returning zero failed checks. A caller consulting only that count could mistake an incomplete evaluation for a clean document. The checker had reported the failure, but its consumer treated the absence of reported violations as evidence that validation had succeeded. The missing distinction was between “no violations found” and “validation did not complete.” Modeling these outcomes separately exposed the error in how the result was interpreted.

    Testing the Tests: Mutation and Fault Injection

    A passing test establishes that the implementation satisfied the checks performed. It does not establish that those checks would detect a relevant defect. Software testing has developed techniques for examining this distinction directly. Mutation testing deliberately introduces small changes into a program and asks whether its tests detect them. A test suite that continues to pass after a relevant defect is introduced may be exercising the code without adequately checking its behavior. Mutation testing has a substantial research history, including work on mutation operators and measures of test adequacy 1819.18. Richard A. DeMillo et al., “Hints on Test Data Selection: Help for the Practicing Programmer,” Computer 11, no. 4 (1978): 34–41, https://doi.org/10.1109/C-M.1978.218136.19. Yue Jia and Mark Harman, “An Analysis and Survey of the Development of Mutation Testing,” IEEE Transactions on Software Engineering 37, no. 5 (2011): 649–78, https://doi.org/10.1109/TSE.2010.62.

    Models can make these experiments more systematic. Rather than introducing arbitrary changes, engineers can derive candidate faults from the properties the model represents. For the job-ownership model in [ref:3.3-constraints-sensors-validators-gates:heading:tests-and-models-work-together], one mutation might remove the generation check from a release operation, allowing an expired worker to clear a newer worker’s claim. A test intended to protect that obligation should reject the mutated implementation. If it does not, the failure is in the evidence used to establish Alignment, even if the original implementation happens to be correct. Model-based mutation testing develops this approach by using mutations of behavioral specifications to assess whether tests can distinguish the intended behavior from plausible alternatives 20.20. Bernhard K. Aichernig et al., “Model-Based Mutation Testing via Symbolic Refinement Checking,” Science of Computer Programming 97 (2015): 383–404, https://doi.org/10.1016/j.scico.2014.05.004.

    Fault injection addresses a related but different question. In these dependency-boundary experiments, it introduces a selected failure during execution: a dependency times out, a response is malformed, or a service becomes unavailable. The failure model identifies which conditions to exercise and what the receiving component must do. In DocAble, the web-layer failure model lets tests inject such conditions at dependency boundaries and examine their propagation. The purpose is not simply to demonstrate that the service encounters an error, but to establish whether its response satisfies the modeled obligation. Fault injection has long been used in dependability evaluation; an explicit failure model helps select experiments and interpret their results 21.21. Mei-Chen Hsueh et al., “Fault Injection Techniques and Tools,” Computer 30, no. 4 (1997): 75–82, https://doi.org/10.1109/2.585157.

    The same reasoning applies to the engineering environment. A validator, sensor, or gate is itself software whose behavior may be incorrect. If a gate is intended to reject a forbidden dependency, deliberately introduce that dependency and verify that the actual gate refuses the change. If a validation result must distinguish success from incomplete execution, inject a checker failure and verify that the consumer does not accept it as success. These experiments test not only whether the check can produce a verdict, but whether the verdict has the required consequence. The incident in [ref:4.4-engineering-the-environment:heading:engineering-capital-depreciates] provides a concrete example: DocAble’s uniqueness checks passed while examining the wrong records. An audit exposed the missing coverage, and the repair added a deliberately introduced duplicate that the corrected check had to reject.

    Agentic implementation changes the economics of this work. Agents can help construct mutants, fault-injection harnesses, and regression tests, making systematic challenges to the checking machinery less expensive. The engineer still decides which faults matter and whether the experiments adequately represent them. A mutation score is not a reliability guarantee: it depends on the mutations selected, and some mutants preserve the program’s behavior. Fault injection likewise covers only the failure conditions and responses exercised. Both techniques provide something more useful than a larger test count: evidence that selected violations can actually be detected.

    3.3.5 One Obligation, Several Ways to Hold It

    A modeled obligation does not imply one particular enforcement technology. Some obligations can be embodied in generated implementation structure; others can be enforced through constraints on agent actions or evaluated through tests and analysis. Tests exercise selected implementation behaviors; model checking examines behavior admitted by an explicit model. Ask what evidence the obligation needs and how the environment should act on it.

    If an invalid state can be excluded by the runtime operation itself, use that constraint where practical. An atomic conditional update can acquire a job only while its database row remains unclaimed. Two competing workers cannot both win that transition. Tests can still check how the surrounding code handles success, refusal, and failure. The runtime primitive and the tests contribute different protections.

    Model checking and model-based testing answer different questions. A model checker asks whether the represented protocol permits a violation within the explored domain. Model-based tests ask whether the implementation behaves as the model requires in the executions they perform. Exploring the model does not itself execute database calls or establish that production code follows the modeled transitions. A counterexample found in the model can guide an implementation test, while a test failure can reveal a distinction missing from the model 2214.22. Christel Baier and Joost-Pieter Katoen, Principles of Model Checking (MIT Press, 2008).

    The obligation determines what further evidence is needed. A test can show that a particular job completed, or that it exceeded a required deadline. The stronger claim that every accepted job eventually terminates concerns all executions the system permits. A temporal model checker can examine that claim over a model, subject to its bounds and assumptions about scheduling and recovery. A fairness assumption must be stated rather than silently treating an operation that can occur as one that eventually will. Confidence in the implementation still depends on how faithfully it follows the modeled behavior 2223.23. Leslie Lamport, Specifying Systems: The TLA+ Language and Tools for Hardware and Software Engineers (Addison-Wesley, 2002).

    DocAble’s document-remediation jobs can outlive a worker attempt. A worker may crash, become slow, or lose contact while another attempt becomes eligible to continue the work. A lease makes current ownership visible and allows apparently abandoned work to be recovered. Its expiry cannot establish that the old worker stopped: a delayed worker may still return. The design therefore distinguishes eligibility to recover the work from permission to perform its protected side effect.

    Figure 3.3-2 shows how DocAble addresses two obligations in this recovery protocol. A runtime constraint prevents competing workers from acquiring the same claim for a protected effect. A separate analysis checks whether the modeled recovery sequence permits a stale worker to invalidate a newer claim. The first restricts what the implementation can do; the second examines behavior that depends on the ordering of several operations.

    DocAble uses a durable compare-and-set to protect the claim for an effect. The operation succeeds only while the stored state matches the required prior state, so competing workers cannot both acquire the same claim. An expired lease or repeated delivery does not bypass this restriction. The constraint governs a particular effect; it does not guarantee that every part of the job executes exactly once.

    The recovery protocol also has obligations that depend on the sequence of operations. Suppose worker A’s lease expires, worker B acquires a newer claim, and A subsequently attempts to release its old claim. The release must not clear B’s ownership. DocAble uses a purpose-built explicit-state checker to explore interleavings of its ownership model within stated bounds and search for violations of this property.§§ This is bounded explicit-state model checking. “Bounded model checking” conventionally refers to bounded executions encoded for SAT/SMT solving; this checker explores an explicitly bounded state space. The analysis establishes a property of the represented protocol, not of every possible implementation. Tests or other evidence must separately establish that the implementation follows it.

    A further obligation concerns eventual completion. The system’s state and recovery models already carried the requirement that every submitted job eventually reach a terminal state. A small TLA+ specification checked with TLC was then developed for that obligation 23. The order matters: engineering identified the required behavior before constructing an analysis of it.

    A check may inform an engineer without controlling the work. When its result is meant to control whether work may proceed, a gate must use it to permit or refuse the action or artifact.

    3.3.6 Margin and Engineering Freedom

    Alignment can do more than determine whether an implementation satisfies an obligation. For quantitative properties, it can also measure how much room remains within the tolerance established by the model. This gives engineers a reason to model non-functional properties explicitly, rather than concentrate only on architecture and behavior. A latency budget, memory bound, or cost ceiling can define an acceptable region within which implementation choices remain open. Chapter 2 introduced tolerances as bounds on acceptable variation and degrees of freedom as choices left open to implementation. Once the environment can measure an implementation against those bounds, engineers can examine not only whether it conforms, but also how close it is to violating them.

    Figure 3.3-3 illustrates this relationship using a response-time obligation of 200 milliseconds. Two implementations complete the same operation in 120 ms and 195 ms, respectively. Both satisfy the requirement, but the first has 80 ms of measured margin while the second has only 5 ms. The model establishes the acceptable region; Alignment supplies the measurements needed to locate each implementation within it. A binary conformance check would accept both and discard this additional information.

    Margin can inform subsequent implementation work. An agent considering a more expensive algorithm or additional processing may have considerable room to explore when measured latency is well below the limit. Near the boundary, the same change may require optimization elsewhere or a different design. The margin does not prescribe which implementation to choose, nor does it guarantee that a proposed change will remain acceptable. It provides evidence that can guide exploration, with the resulting implementation evaluated again against the obligation.

    The evidence also informs the engineer. Shrinking margin may indicate that the current design has little capacity to absorb additional work or operating variation. The engineer can investigate the cause, reconsider the architecture, allocate a more specific performance budget, or introduce an earlier warning threshold. The appropriate response is not necessarily to tighten the tolerance. The original bound may remain correct even when the implementation approaches it. In this way, Alignment returns information to Modeling: measurements obtained from one implementation can improve the representations and decisions governing the next engineering task.

    This reasoning applies where the model defines a meaningful quantitative boundary and the environment can measure the relevant behavior. Latency, memory consumption, cost, and capacity are familiar examples. The measured margin also depends on the workload and conditions under which it was obtained; headroom observed in one setting is not a guarantee under another. Many software obligations are discrete instead. A dependency is permitted or forbidden, and a state transition is legal or illegal. Such properties may admit measures of risk, but they do not necessarily have a useful distance to failure. For them, conformance may be the appropriate evaluation.

    The broader point is that Modeling and Alignment inform one another. Modeling establishes which variation is acceptable. Alignment evaluates actual behavior against that model and, where the property permits, measures the remaining margin. This makes quantitative models particularly useful: they can guide implementation choices even when no obligation has been violated. Engineers have reason to model such properties not only to reject unacceptable implementations, but also to make the remaining freedom visible. Measurements from one implementation can then inform the models and decisions governing the next engineering task.

    3.3.7 Positive and Negative Constraints

    A negative constraint prohibits an action, such as accessing a document’s internal representation except through a sanctioned interface. But an agent might find another route to the same effect without using that interface. A complementary positive constraint requires evidence that a protected operation passed through an authorized path. This resembles remote attestation, where a receiving mechanism evaluates evidence supporting a claim 24.24. Henk Birkholz et al., Remote ATtestation procedureS (RATS) Architecture, RFC 9334 (Internet Engineering Task Force, 2023), https://doi.org/10.17487/RFC9334.

    The receiving boundary can require such evidence without enumerating every possible bypass. Depending on the stakes, engineers may also need to establish its reliability. Requiring an attribution record does not establish that the record is authentic or accurately describes the operation.

    3.3.8 The Freedom a Control Preserves

    Alignment should preserve the implementation freedom that Modeling deliberately leaves open. A control can exclude an unacceptable realization, but it can also rule out alternatives that satisfy the stated obligations. Operational simplicity or the cost of assurance can justify some restrictions. As implementation becomes cheaper, more of the alternatives that a control excludes may be worth exploring.

    For consequential choices whose effects are still uncertain, engineers can defer a commitment until the last responsible moment. Waiting can yield useful information, but it can also make a later change more expensive. Agents can produce prototypes and experiments sooner, while controls protect the obligations already understood. The tradeoff depends on which realizations satisfy the stated obligations and which the environment actually permits.

    We can describe this tradeoff with sets. Let R be the possible realizations of the work. Each obligation Oi⊆R is the set of realizations satisfying it, so the acceptable realizations are A=O1∩…∩On.

    For a fixed control configuration and decision context, let Cj⊆R be the set of realizations permitted by enforcing control j, whether a direct constraint or a gate. When every applicable control must permit a realization, the environment permits P=C1∩…∩Cm. A gate can exclude a realization that satisfies all direct constraints, for example because required evidence is missing. Sensors can supply evidence for that decision without themselves restricting P. The permitted region can change as the evidence or controls change. Two kinds of mismatch appear as set differences:

    underconstraint: P∖Aoverconstraint: A∖P

    Underconstraint leaves unacceptable realizations permitted; it threatens correctness. Overconstraint excludes acceptable realizations; it sacrifices useful engineering freedom. Table 3.3-2 classifies realizations by acceptability and permission.

    Table 3.3-2. Acceptability versus permission. Obligations determine acceptability; enforcing controls determine permission. Underconstraint permits unacceptable realizations, while overconstraint excludes acceptable alternatives.
    RealizationsPermittedExcluded
    AcceptablePreserved freedomOverconstraint
    UnacceptableUnderconstraintCorrect exclusion

    Making P coincide with A is an idealization, not always a practical or even desirable goal. An engineer may deliberately exclude acceptable alternatives — for operational simplicity, for consistency, or for assurance. Comparing the two regions helps engineers identify that restriction and decide whether its benefit justifies the lost freedom.

    3.3.9 What Counts as a Mechanism

    Policy, guidance, and governance mechanisms contribute different things to engineering work. A model can state a policy, and a playbook can explain how to follow it. Sensor evidence and check results can help engineers assess the work without changing what the environment permits. Enforcement requires a constraint on the relevant action or a gate that evaluates a condition and permits or refuses passage.

    For the reporting service, an agent can consult the architectural model when choosing how to obtain billing data. The dependency validator uses the same model to check the relationships extracted from the code. A build gate can require that check to pass. A deployment tool can also derive network permissions from the model, allowing API calls while denying direct database connections. Each use needs its own implementation: supplying the model to the agent does not install the validator or the permissions.

    A governance package combines these mechanisms so they can be maintained and used together. Within the package, keep track of which mechanism produces evidence, which evaluates it, and which restricts or refuses work. That distinction makes it easier to diagnose a failure without confusing an incorrect judgment with a failure to enforce it.

    Some mechanisms can be designed before the first autonomous change; others become visible only after the environment fails. The next section shows how those failures become durable structure.
