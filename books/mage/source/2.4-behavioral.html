    §2.4 Behavioral Models: What May Happen?

    A structural model describes relationships among parts of a system. A behavioral model describes how the system acts or changes over time. Depending on the question, we might model messages exchanged in a protocol, steps in a workflow, or a quantity that changes continuously. Here we focus on a common choice for software systems: discrete states and the events that move a system between them. With such a model, we can ask whether a job can finish before it starts, or whether a job that starts will ever finish.

    2.4.1 States, Transitions, and Behavioral Analysis

    Suppose a service processes jobs that may be waiting, running, completed, or failed. Can a job report completion before anyone has started it? To find out, we need to know where a job begins, which event starts it, and from which states the service permits completion. We can set aside the database schema, scheduling algorithm, and retry machinery for now. If a job can finish too early, we ought to be able to see how in a model small enough to trace by hand.

    Constructing a Behavioral Model

    Four states and three events suffice. Let S={IDLE,RUNNING,DONE,FAILED} be the states, with each job starting in IDLE. The events are E={start,finish,fail}. We still need to say which events are permitted in each state and where they take the job.

    What an event does depends on the state in which it occurs. The following partial function δ:S×E⇀S gives the next state for each permitted pair:

    δ(IDLE,start)=RUNNING,δ(RUNNING,finish)=DONE,δ(RUNNING,fail)=FAILED.

    Try finish from IDLE. There is no entry for that pair, so the model forbids the transition. Now try start followed by finish. The first entry takes the job to RUNNING, from which the second takes it to DONE. Both DONE and FAILED are terminal.

    The model settles when a job may finish while leaving the engineer free to choose how to implement it. An agent might store the state in a database, manage jobs through a queue, or use an in-memory scheduler. A state-machine interpreter can consult the entries directly. A test generator can use those same entries to produce a sequence of events and predict the state the implementation should report afterward.

    A failed attempt need not mean a failed job. In Figure 2.4-1, a repairable failure moves a running job into Retrying while the retry budget remains. Let r count retries already started, initially zero. Starting another attempt increments r and returns the job to Running. A nonrepairable failure, or a failure after all N retries have been used, takes the job to Failed. A job can therefore succeed after an earlier attempt failed, while the retry budget bounds the additional attempts.

    Properties and Analyses

    Starting at Pending and following permitted arrows gives us one possible execution of the model. Trace Pending, Running, Retrying, Running, Succeeded. That path shows that success after a retry is reachable. Here the arrows specify behavior the service permits. In a model derived from an implementation, the same path would describe behavior to evaluate against a requirement.

    One path can establish reachability, and one bad path can disprove a safety requirement. Suppose the requirement is that a job must enter Running before it reaches Succeeded. Finding one execution that does so leaves all the other executions to consider. Instead, search for a path from Pending to Succeeded that avoids Running. Any such path would show exactly how premature completion could occur; in the figure, there is none.

    A job can obey every ordering rule and still never finish. The requirement that every started job eventually succeeds or fails is a liveness property. A limit of three retries bounds the number of attempts, but says nothing about how long a worker may remain in Running. Observing one slow attempt cannot settle whether it will ever finish.

    To investigate progress, we must say what can keep a job waiting and what allows it to resume. If the service relies on a timeout, represent what happens when it fires and state the assumption that it will be delivered. We can then ask whether any execution under those assumptions can avoid both terminal states indefinitely. Temporal model checking evaluates such requirements over executions 1.1. Christel Baier and Joost-Pieter Katoen, Principles of Model Checking (MIT Press, 2008). For a more complex lifecycle, statecharts can organize related states hierarchically and represent concurrent activity 2.2. David Harel, “Statecharts: A Visual Formalism for Complex Systems,” Science of Computer Programming 8, no. 3 (1987): 231–74, https://doi.org/10.1016/0167-6423(87)90035-9.

    2.4.2 DocAble: Job Lifecycles and Recovery

    DocAble distributes document accessibility work across workers that may fail or lose their assignments. Recovery raises two behavioral questions beyond the simple job lifecycle in the preceding subsection. Can a worker publish a recovered result in an unsafe order? Can a former owner return and interfere with a newer assignment? The first requires a model of publication states; the second requires a model of ownership across competing workers.

    Publishing a recovered result

    A worker recovering a document job may have a corrected artifact available locally before uploading it to persistent storage. If the worker updates the database record first and then crashes, the record can point to an artifact that other workers cannot retrieve. What ordering of publication and database updates prevents this failure?

    Recovery-ordering model · Behavioral

    • Engineering question — In what order may recovery publish an artifact and update the record that refers to it?
    • Model — a transition system over the recovery lifecycle; the decisive fact is a transition that does not exist.
    • Property — the database record may refer to the fallback artifact only after that artifact has been uploaded to persistent storage.
    • Quality attribute — data integrity; crash-safety.

    Figure 2.4-2 represents the recovery operation using three states. In FALLBACK_STAGED, the corrected artifact exists locally; in FALLBACK_UPLOADED, it has been published to durable storage; and in DB_UPDATED, the database refers to it. The permitted path passes through all three states. The prohibited transition from FALLBACK_STAGED directly to DB_UPDATED represents the unsafe ordering: the database would refer to an artifact that had not yet been published.

    To check the ordering property, search for an execution that reaches DB_UPDATED without first visiting FALLBACK_UPLOADED. The three-state model has no such execution. In a larger lifecycle, checking only for the direct forbidden transition would be insufficient: another sequence of transitions might reach DB_UPDATED while bypassing publication. This is a safety property, not a liveness guarantee. A worker could wait or retry indefinitely without violating the ordering requirement.

    The three-state recovery model is a reduction for checking publication order. DocAble’s fuller job lifecycle includes queued, leased, remediating, and completed or failed states. That model can address broader workflow questions when it includes the relevant transitions; the smaller recovery model keeps only what the ordering question needs.

    Distinguishing a current owner from a returning one

    DocAble leases each in-flight job to one worker. Suppose worker A stalls and its lease expires. Worker B acquires the job, but A later returns and attempts to release its old assignment. How can the system distinguish A’s obsolete claim from B’s current one? Table 2.4-1 distinguishes several constructs for representing access and ownership. DocAble combines two: a claim records the assignment, and a lease limits its lifetime.

    Table 2.4-1. Constructs for access and ownership. Locks, leases, capabilities, and claims express different aspects of a worker's right to act.
    ConstructWhat it expresses
    LockCoordinates access to a resource. An exclusive lock admits one holder at a time.
    LeaseGrants a right for a limited period; expiry can make that right available for reassignment 3.3. Cary G. Gray and David R. Cheriton, “Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency,” Proceedings of the Twelfth ACM Symposium on Operating Systems Principles (New York), 1989, 202–10, https://doi.org/10.1145/74850.74870.
    CapabilityCarries authority to perform specified operations on a resource; that authority need not be exclusive.
    ClaimRecords a worker’s assignment to a job and the conditions under which that assignment is valid.

    The model represents ownership through a current claim relating a worker to a job. A job is leased exactly when it has such a claim; ownership and lease status are not separate facts that can disagree within this model. Each claim also records a generation and a lifetime. Expiry makes the job available for reassignment, and a new assignment advances the generation. The generation distinguishes successive claims even when they concern the same job.

    In-flight lease · Ownership

    • Engineering question — Who currently owns this in-flight work, and can a returning stale owner disturb the current claim?
    • Model — a claim relating a worker to a job, stamped with a generation and a lifetime; reclaim advances the generation.
    • Property — a stale claim cannot clear or supersede the current one.
    • Quality attribute — correctness under concurrency; crash-safety.

    Figure 2.4-3 follows one possible execution. Worker A acquires generation 7, then stalls until its lease expires. Worker B reclaims the job at generation 8. When A returns and attempts to release generation 7, the operation must not clear B’s current claim. The job remains owned by B at generation 8. The generation number makes the stale operation distinguishable from a release by the current owner. Without that distinction, A’s delayed release could clear B’s valid assignment.

    The illustrated execution is only one possible ordering of events. To investigate the invariant, explore the interleavings of lease expiry, reassignment, and delayed release. At each reachable configuration, check whether a release from an earlier generation can clear or supersede the current claim. A counterexample would identify an event sequence that violates ownership; checking the reachable configurations establishes the property within the model’s declared scope.

    The publication model separates a local artifact from a durably stored one. The ownership model separates a current claim from a superseded one. In each case, the useful addition is a distinction that changes whether a state change is acceptable. The models make those distinctions available for analysis; the later Alignment chapter examines the mechanisms that enforce them.

    Notice what this model omits: the processing topology. Ownership, generation, lifetime, and reclamation matter to the question of who controls a job; how the job's work is partitioned does not. DocAble's implementation changed over time to improve performance while preserving those ownership semantics. We changed the pointers to the code, but not the model. The ownership properties could therefore remain invariants across those changes. The inset shows how a relationship built into the model can become an invariant when an implementation stores its parts separately.

    FORMAL METHODS

    Inset — What is an invariant?

    An invariant is a property required to hold over a declared domain of states, structures, or observations. In a behavioral state machine, the invariant may be a predicate that must hold in every reachable state; in a structural model, it may require every observed dependency to belong to a declared set; in a measurement model, it may require a quantity to remain within a hard capacity bound. State both the property and the domain the checker claims to establish it over.

    Take a behavioral illustration. A job carries two fields at once — a status of free, leased, or done, and a lease_owner that names the holding worker or is empty. At the model level, leased-iff-owner was a definition; an implementation that represents the two sides as separately written fields turns it into a property that can fail, which is exactly why you write the invariant down. "A job is leased if and only if it has an owner" is a predicate over the pair: (status == "leased") == (lease_owner is not None). A free status with a lingering lease_owner is a stale lease; a leased status with no owner is a lost lease. Separating the two writes can make either inconsistent state reachable, and both break the predicate. The predicate becomes mechanically meaningful when a checker evaluates it over the declared reachable state space:

    STATES = product({"free", "leased", "done"}, {None, "worker-1", "worker-2"}) def invariant(s): # leased iff owned return (s.status == "leased") == (s.lease_owner is not None) assert all(invariant(s) for s in reachable_states()) # check every reachable state

    A lease illustrates how one representation can answer several classes of question. Its owner identifies who currently controls a job. Its generation and lifetime distinguish current claims from stale ones and support reasoning about expiry and reclamation. Counting the current claims across jobs gives a measurement of how much work is in flight. These questions concern ownership, behavior, and capacity, yet they draw on the same represented facts.

    The overlap follows from the distinction introduced at the opening of the chapter: model classes identify engineering questions, not mutually exclusive data structures. One representation can serve several questions when it preserves the facts each requires. §2.6 develops this idea further by connecting models through shared identities.

    Ownership introduced permission implicitly: a stale claimant may not clear a current lease. The next section examines decisions directly, including permissions and how to choose what should happen next.
